## 2. 設計內容

### 2.1 函式介面

```c
uint32_t rotl_ref(uint32_t rs1, uint32_t rs2);
```

| 決策 | 原因 |
|---|---|
| 參數與回傳值都用 `uint32_t` | 旋轉是位元操作,不需要正負號。無號數的 `>>` 一定是**邏輯右移**(左邊補 0)。若用 `int32_t`,負數右移在 C11 是 implementation-defined,GCC / Clang 會做算術右移(補 1),結果錯誤 |
| `rs2` 也用 `uint32_t`,函式內取 `rs2 & 31` | 規格只用 `rs2` 的低 5 位元。`rs2 = −1` 傳進來是 `0xFFFFFFFF`,取低 5 位元後為 31,與規格一致 |
| `n == 0` 單獨回傳 `rs1` | 照公式計算會得到 `rs1 >> 32`。C11 §6.5.7 規定移位量大於等於型別寬度是**未定義行為**,編譯器可以產生任何結果 |

### 2.2 實作

```c
uint32_t rotl_ref(uint32_t rs1, uint32_t rs2)
{
    uint32_t n = rs2 & 31u;
    if (n == 0)
        return rs1;
    return (rs1 << n) | (rs1 >> (32u - n));
}
```

原始碼:[`c_baseline/rotl.c`](../c_baseline/rotl.c)

**反例**(`make ub-demo`):把 `n == 0` 的分支拿掉,`n = 4` 時結果正確,`n = 0` 時 UBSan 回報:

```
runtime error: shift exponent 32 is too large for 32-bit type 'uint32_t'
```

RISC-V 和 x86 的移位硬體都只取移位量的低 5 位元,`x >> 32` 在硬體上會變成 `x >> 0`,結果 `x | x = x` 看起來剛好正確。但在 C 語言層級這是未定義行為,編譯器最佳化時可以假設它不會發生,所以不能依賴「剛好算對」。

**假設**:`uint32_t` 為 32 位元;主機與 RISC-V 目標皆為二補數。

### 3.1 5 Whys 推理鏈

決策:`rotl_ref` 為什麼要把 `n == 0` 單獨處理?

| 層 | 為什麼? | 答案 | 驗證方式 |
|---|---|---|---|
| 1 | 為什麼 `n == 0` 要單獨處理? | 照公式代入 `n = 0`,右半部會變成 `rs1 >> (32 − 0)`,也就是 `rs1 >> 32` | 手算代入公式;測資 T02(`rs2 = 0`)與 T05(`rs2 = 32`,取低 5 位元後也是 `n = 0`) |
| 2 | 為什麼 `rs1 >> 32` 不能寫? | `rs1` 是 32 位元的 `uint32_t`,C11 規定移位量大於等於型別寬度是未定義行為 | C11(N1570)§6.5.7 第 3 段;`make ub-demo` 在 `n = 0` 時 UBSan 回報 `shift exponent 32 is too large for 32-bit type` |
| 3 | 實際執行明明「算對」了,為什麼還不行? | 在組員的 Mac(Apple clang 21,arm64)上不開 UBSan,錯誤寫法 `n = 0` 時輸出 `0x12345678`,剛好正確,是因為硬體的移位只取移位量低 5 位元。但未定義行為代表 C 標準對結果**沒有任何保證**,換編譯器或最佳化等級都可能不同 | `cc -std=c11 -O0`、`-O2` 分別編譯 `c_baseline/ub_demo.c` 再執行 `./a.out 0`,兩者都輸出 `0x12345678`;C11 §3.4.3 對未定義行為的定義 |
| 4 | 為什麼不能接受「沒有保證」? | `rotl_ref` 是參考實作,同一份程式要在不同編譯器與最佳化等級下都給出同一個答案(主機上的測試用 `-O2`,之後還要給 RISC-V 編譯器編譯) | `Makefile` 的 `test-c` 用 `-O2` 編譯;`make test-ubsan` 以同一組測試確認 `rotl_ref` 沒有未定義行為 |
| 5 | 為什麼參考實作一定要可靠? | 之後的組合語言版本與自訂指令都要拿它當標準答案比對,它若出錯,後面所有驗證都會跟著失效 | `make test-c`:16 組測資全過,並與另一個獨立寫法(每次只旋 1 位)交叉比對 1000 × 69 = 69,000 次全部一致 |

結論:`n == 0` 單獨處理,是為了讓參考實作在 C 語言層級完全沒有未定義行為,不依賴特定硬體或編譯器「剛好算對」。

## 4. 遭遇的問題與解法

在組員的 Mac(Apple clang 21,arm64)上執行 `make ub-demo`,最後一行出現 `make: *** [ub-demo] Abort trap: 6`,看起來像是建置失敗。用 `echo $?` 查 make 的結束碼,結果卻是 0;再對照 `Makefile`,發現那一行寫成 `-./build/ub_demo 0`。原因是 `ub_demo` 以 `-fno-sanitize-recover=all` 編譯,UBSan 一抓到 `n = 0` 的「移位 32」就讓程式中止(Abort trap: 6),而指令前面的 `-` 讓 make 忽略這個錯誤。也就是說,這個報錯是反例**預期中**的結果,正好證明沒處理 `n = 0` 的寫法有未定義行為,程式不需要修改。為了確認,我們再把 `ub_demo.c` 不加 UBSan 編譯:`n = 0` 時輸出 `0x12345678`,看起來完全正確。可見沒有 sanitizer 時這個錯誤根本看不出來,這也是 `make test` 要另外跑 `test-ubsan` 的原因。

## 5. 白話說明

ROTL 就像轉一個串了 32 顆珠子的手環:往左轉 n 格,從左邊掉出去的珠子會從右邊接回來,一顆都不會少。程式用「左移 n 格」加上「右移 32 − n 格」拼出這個效果。卡住的地方是轉 0 格:照公式要右移 32 格,而 C 語言對這件事沒有規定結果。在 Mac 上不開檢查工具時,錯誤寫法剛好算對,完全看不出問題;開了 UBSan 才被抓到,程式直接中止。所以參考實作先判斷:轉 0 格就直接回傳原值。
